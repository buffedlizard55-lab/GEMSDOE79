The [0, 1] portal error — cause and prevention

DrivenData rejects values outside [0, 1]. In this data family the trap is the float32 nodata sentinel −3.4028235e+38 carried inside the footprint (3,061 cells of training_features.tif) and nodata tags read as values. Our writer refuses to write anything non-finite or out of range (no silent clipping), sets nodata=None, then re-opens the written TIFF and the single-TIFF ZIP and verifies: one band, float32, EPSG:32611, exact transform/shape, min 0.0, max 1.0, zero NaN. That is a local guarantee, not organizer acceptance.

How a future approved submission works, step by step

  1. Clear every gate first. Source provenance, per-feature leakage canaries (AUC ≤ 0.90), buffered whole-component hide-and-recover beating a matched incumbent with a paired 95% CI above 0, novelty on surface and final dots vs the full registry, and the on-disk format checks.

  3. Download the approved file (the .tif above only after a future run flips its verdict — never this DO-NOT-SUBMIT artifact). Keep its unique name; copy its ≤140-character note from the identity panel.
  4. On the DrivenData form: “File to submit” → choose the .tif (or the single-TIFF .zip); “Note (optional)” → paste the note; submit within the verified cap.
  5. Save the receipt. Record file name + SHA-256 + the score shown by the server. Only that receipt makes a score ORGANIZER-CONFIRMED and lets the next session learn from it.
